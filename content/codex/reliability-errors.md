## Обробка помилок

Ланцюжок типізованих обробників **від конкретніших до загальніших**:

```ts
try {
  const res = await client.messages.create({ ... });
} catch (error) {
  if (error instanceof Anthropic.NotFoundError) { /* виправити запит */ }
  else if (error instanceof Anthropic.RateLimitError) { /* backoff */ }
  else if (error instanceof Anthropic.APIStatusError) { /* за статусом */ }
  else if (error instanceof Anthropic.APIConnectionError) { /* повтор */ }
}
```

Один загальний `catch` втрачає різницю між 429 (повторити) і 400 (повторювати безглуздо). Рядковий пошук по тексту помилки ламається тихо: тексти змінюються.

## 429 і backoff

Чекати згідно з `retry-after`, повторювати з **експоненційним відступом і джитером**. Джитер тут не менш важливий за backoff: без нього всі клієнти повторюють синхронно й самі створюють наступну хвилю обмежень.

Негайний повтор поглиблює перевантаження.

## stop_reason

| Значення | Що робити |
|---|---|
| `end_turn` | Нормальне завершення |
| `tool_use` | Виконати інструмент, повернути `tool_result` |
| `max_tokens` | Обрив на межі виводу: підняти `max_tokens`, для великих значень — streaming |
| `refusal` | Відмова з міркувань безпеки; деталі в `stop_details` |
| `pause_turn` | Пауза в агентному потоці, можна продовжити |

`stop_details` заповнене **лише** при `refusal` — перед читанням завжди перевіряйте.

Занизький `max_tokens` — хибна економія: обрізана відповідь означає повторний запит і подвійну оплату.

## Спостережуваність

Логувати:

- `usage` — токени й показники кешу: відповідає на «чому дорого»;
- `stop_reason` — «чому обрізано чи відмовлено»;
- виклики інструментів з аргументами й результатами — «що агент насправді робив».

Не логувати: ключі API (для кореляції є ідентифікатор запиту) і повні користувацькі дані без обмежень.
