## Ієрархія надійності

| Спосіб | Гарантія |
|---|---|
| `output_config.format` зі схемою | ✓ валідується API |
| Tool use зі `strict: true` | ✓ аргументи відповідають схемі |
| Прохання «відповідай лише JSON» | ✗ здебільшого працює |
| Prefill символом `{` | ✗ **400 на сучасних моделях** |
| Регулярка для вирізання JSON із тексту | ✗ рятувальний круг |

⚠️ Використовуйте `output_config: { format: {...} }`, а не застарілий параметр `output_format`.

## strict tool use

```json
{
  "name": "create_ticket",
  "description": "...",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "priority": { "type": "string", "enum": ["low", "medium", "high"] },
      "title": { "type": "string" }
    },
    "required": ["priority", "title"],
    "additionalProperties": false
  }
}
```

`strict` — поле **самого інструмента**, поруч із `name` та `input_schema`, а не всередині `tool_choice`. Схема має бути закритою: без `additionalProperties: false` гарантії немає.

Несумісний із programmatic tool calling.

## Схема — це теж промпт

- `enum` там, де множина значень скінченна;
- осмислені імена й описи полів;
- `required` для обов'язкових;
- ✗ не робіть усі поля рядками «про всяк випадок» — втрачається типізація.

## Валідація і ретрай

Повторювати той самий запит без змін безглуздо. Ретрай має нести **конкретну помилку валідації**:

> «поле `amount` має бути числом, отримано рядок "12,50"»

Це той самий принцип, що й структуровані помилки інструментів ([[tool-schemas-errors]]).

## Не ховайте збої

Тихе `try/catch` із пропуском запису — найгірший варіант: дані зникають, і про це дізнаються з квартального звіту. Невдачі мають потрапляти в чергу для розбору.
