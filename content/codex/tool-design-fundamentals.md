## Опис інструмента — це промпт

Поле `description` передається моделі в кожному запиті. Саме за ним вона вирішує, **коли** викликати інструмент; схема каже лише **як**.

Порівняйте:

- ✗ `"Search"`
- ✓ `"Шукає за повнотекстовим індексом документів. Для пошуку за ідентифікатором використовуйте get_document."`

Різниця між цими двома описами — це різниця між зациклюванням і роботою.

## Неперетинні межі

Інструменти, що перекриваються (`get_user` і `fetch_user_data`), дають хаотичні виклики. Лікування — об'єднати або чітко розмежувати призначення в назвах і описах.

`tool_choice` для примусового вибору тут не рятує: він ламає агентність.

## Чесноти хорошого інструмента

| Властивість | Чому |
|---|---|
| Економний вивід із фільтрами й пагінацією | Контекст — обмежений ресурс |
| Опис пояснює *коли* застосовувати | Модель обирає за описом |
| Структуровані помилки з підказкою | Дає шанс на самовиправлення |
| Компактна поверхня параметрів | Менше можливостей викликати некоректно |

Антипатерн: «повертати максимум даних, щоб не було другого виклику». Кілька цілеспрямованих викликів дешевші за дамп на 50 тисяч токенів.

## Багато інструментів

При кількох десятках інструментів якість вибору падає, а описи з'їдають контекст. Механізм API — **tool search**: рідковживані інструменти позначають `defer_loading: true`, і їх визначення вантажаться на вимогу.

Умова: сам інструмент пошуку не може бути відкладеним, і принаймні один інший теж — інакше 400.

## Bash чи вузькі інструменти

| | Вузькі інструменти | Узагальнений bash |
|---|---|---|
| Валідація аргументів | ✓ схема | ✗ довільний рядок |
| Передбачуваність | ✓ | ✗ |
| Гнучкість | обмежена | ✓ |

Bash виправданий у пісочниці для відкритих задач. Довільний SQL в інструменті бази — це `eval` для продакшн-бази: замініть на параметризовані операції з таймаутом.
