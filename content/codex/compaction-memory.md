## Два різні механізми

| Механізм | Що робить |
|---|---|
| **Компакція** | Підсумовує ранній контекст (beta `compact-2026-01-12`) |
| **Context editing** | **Видаляє** старі результати інструментів або блоки міркувань (`clear_tool_uses_*`, `clear_thinking_*`) |

Різниця у ціні втрати: підсумок зберігає суть у стислій формі, очищення прибирає повністю. Старі результати інструментів зазвичай не шкода видалити; хід роботи краще підсумувати.

## Головна пастка компакції

Компакція повертає в `content` блоки, якими API замінює стиснуту історію на наступному кроці.

```ts
// ✓ правильно
messages.push({ role: "assistant", content: response.content });

// ✗ тиха втрата стану
messages.push({ role: "assistant", content: textBlock.text });
```

Якщо зберігати лише текст, блоки компакції зникають. Помилки не буде — буде тиха втрата контексту.

## Стратегії для довгих сесій

- зберігати проміжні результати у **файли** й повертатися до них за потреби;
- делегувати обсяг читання **субагентам** ([[subagents]]);
- підсумовувати завершені етапи в компактний стан.

Усі три про одне: тримати у вікні лише актуальне.

`max_tokens` і `effort` до цієї проблеми відношення не мають — це стеля виводу й глибина міркування, а не вхідний контекст.

## Стан має пережити компакцію

Якщо агент після компакції «забуває», що вже зробив, — потрібна **зовнішня пам'ять**: файл прогресу, який агент оновлює після кожної одиниці роботи й перечитує на початку етапу.

Вона детермінована, видима людині й переживає навіть перезапуск процесу.
