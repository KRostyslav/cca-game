## Яку проблему розв'язує

До MCP кожна інтеграція писалася під конкретний застосунок. **Model Context Protocol** стандартизує спосіб, у який застосунки надають моделям інструменти й контекст: один сервер працює з будь-яким MCP-клієнтом.

## Архітектура

```
Host-застосунок (Claude Code, десктопний клієнт, ваш бекенд)
   ├── MCP-клієнт ──→ MCP-сервер A
   ├── MCP-клієнт ──→ MCP-сервер B
   └── MCP-клієнт ──→ MCP-сервер C
```

Модель **не** підключається до серверів сама: з'єднання тримає застосунок, а модель бачить надані ним інструменти. Одне з'єднання клієнт-сервер на кожен сервер — це і межа довіри, і межа конфігурації.

## Три примітиви

| Примітив | Хто ініціює використання |
|---|---|
| **Tools** | Модель |
| **Resources** | Застосунок (дані для читання) |
| **Prompts** | Користувач (шаблони) |

Це розмежування визначає, що куди складати. Якщо рішення про використання приймає модель — це tool.

## Транспорти

- **stdio** — локальний сервер як підпроцес; без портів і мережевої автентифікації.
- **Streamable HTTP** — віддалений сервер; авторизація за OAuth 2.1.

## Для моделі різниці немає

MCP-інструменти потрапляють у контекст такими самими визначеннями, як інструменти в полі `tools`. Різниця — хто їх постачає й виконує. Тому якість опису важлива так само ([[tool-design-fundamentals]]).
