## Порядок блоків

Рендеринг запиту: **`tools` → `system` → `messages`**. Звідси єдине правило компонування:

> Стабільне — попереду, волатильне — позаду.

```
[стабільні інструменти]
[стабільний системний промпт]      ← точка кешування
[стабільний довідковий матеріал]
[змінні дані запиту]
[питання]
```

Одна дата чи ім'я користувача на початку системного промпта знецінює кеш для всього, що йде далі. Це найчастіша причина нульових `cache_read_input_tokens` ([[prompt-caching]]).

## Абсолютні вимоги = перевірка, не прохання

«Ніколи не вигадуй характеристик» у промпті знижує частоту, але не дає гарантії. Гарантію дає структура:

- структурований вивід із полем-джерелом для кожного твердження;
- автоматичне відхилення відповіді, де є твердження без джерела;
- для роботи з документами — механізм citations, що прив'язує цитату до конкретного місця в документі.

## Аудит при міграції моделі

Промпти накопичують милиці під конкретну модель. Після переходу на нову:

- приберіть обхідні прийоми, написані під стару поведінку;
- спростіть надмірно директивні покрокові інструкції;
- переоцініть на своєму датасеті ([[prompt-evals]]).

Додавати нові інструкції поверх застарілих — типова помилка: суперечності множаться, а якість падає далі.

## Оптимізація вартості: порядок

1. Гігієна вхідних токенів — не класти зайвого.
2. Кешування стабільного префікса.
3. Економні інструменти ([[tool-schemas-errors]]).
4. І лише потім — компроміси якістю: нижчий `effort`, слабша модель.

Кроки 1–2 безкоштовні за якістю. Починати з кроку 4 — передчасний компроміс.
