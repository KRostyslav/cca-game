## Матриця вибору

| Ситуація | Рішення |
|---|---|
| Кілька host-застосунків потребують тієї самої інтеграції | **MCP-сервер** |
| Чутливі дані не мають залишати периметр | **Self-hosted MCP-сервер** |
| Одна операція в одному застосунку | **Звичайний інструмент** із вузькою схемою |
| Потрібен готовий публічний конектор і ризик прийнятний | Сторонній MCP-сервер |
| Потрібна довільна мережева активність | ✗ майже ніколи |

## Коли MCP окупається

MCP дає **переносність і повторне використання**: сервер описує інструменти один раз, будь-який MCP-клієнт їх підхоплює, оновлення доходить до всіх host-застосунків без правок у них.

Спільна бібліотека цього не дає: у десктопний клієнт нічого не заімпортуєш. Спільний REST API теж — визначення інструментів довелося б дублювати в кожному клієнті.

## Коли MCP — надлишок

Одна операція («надіслати повідомлення в один канал Slack») в одному застосунку. Сервер, конфігурація й супровід заради однієї функції не окупляться. Дешевше й безпечніше — звичайний інструмент із вузькою схемою.

Ще гірший варіант — дати агенту `curl` і токен: жодної валідації, необмежена поверхня дій.

## Коли поведінка агента змінилася після підключення

Перевіряйте **описи інструментів сервера**. Це чужий текст у вашому промпті: він може заохочувати до дій, яких ніхто не просив. Технічна межа — дозволи, а не сподівання на добропорядність опису.
