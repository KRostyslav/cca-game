## Як працює

Кешування — це **збіг префікса**. Будь-яка зміна байта в префіксі знецінює кеш для всього, що йде після неї. Жодної семантики: збіг має бути точним.

Порядок рендерингу: **`tools` → `system` → `messages`**.

## Компонування

> Стабільне — попереду, волатильне — позаду.

```ts
await client.messages.create({
  model: "claude-opus-5",
  max_tokens: 16000,
  system: [
    { type: "text", text: STABLE_SYSTEM, cache_control: { type: "ephemeral" } },
  ],
  messages: [...history, { role: "user", content: question }],
});
```

Максимум 4 точки кешування на запит. Мінімальний кешований префікс залежить від моделі (приблизно 512–4096 токенів) — коротший просто не кешується, без помилки. TTL за замовчуванням 5 хвилин, є варіант на годину.

## Тихі інвалідатори

| Причина | Прояв |
|---|---|
| Поточна дата/час у системному промпті | Кеш ніколи не влучає |
| Недетермінований порядок ключів при серіалізації інструментів | Випадкові промахи |
| Набір інструментів, що змінюється від запиту до запиту | Кеш ламається з першого блоку |
| Ім'я користувача на початку промпта | Знецінює весь наступний вміст |

Довжина промпта інвалідатором **не** є: великий стабільний префікс дає найбільшу економію.

## Діагностика

Єдине пряме джерело правди — поле `usage`:

- `cache_creation_input_tokens` — записано в кеш (≈1.25× вартості);
- `cache_read_input_tokens` — попадання (≈0.1× вартості);
- `input_tokens` — некешоване.

Якщо `cache_read_input_tokens` стабільно нуль при схожих запитах — шукайте інвалідатор у префіксі. Латентність для цього не показник: вона шумна.
