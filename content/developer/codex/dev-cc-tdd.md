## Чому TDD особливо добре працює з агентом

Claude працює найкраще, коли має **об'єктивну ціль перевірки**: тести, type-check (`tsc --noEmit`), лінтер, скриншот проти макета. Власна впевненість моделі чи кількість змінених рядків такою ціллю не є.

Скажіть явно «працюємо за TDD». Без цього модель схильна одразу писати реалізацію або мок-реалізацію, а тести під неї підганяти. Тести й реалізація одним кроком — погано: тести віддзеркалять код разом із його помилками.

## Цикл

1. Написати тести за очікуваними входами й виходами.
2. Запустити й **переконатися, що падають**. Тест, зелений без реалізації, нічого не перевіряє.
3. Закомітити тести — тепер будь-яка їхня зміна видна в diff.
4. Реалізувати, **не змінюючи тестів**, доки не стануть зеленими.
5. Закомітити реалізацію; рефакторинг — на зелених тестах.

Для бага: спершу падаючий тест, що відтворює проблему, потім виправлення.

## Ознаки підгонки

| У diff | Чому погано |
|---|---|
| `toBe(42)` → `toBeDefined()` | послаблена специфікація |
| `it.skip`, закоментований тест | тест вимкнено |
| `it.only` | решта тестів файлу не запускається, «зелений» оманливий |
| гілка під конкретні тестові дані | хардкод замість логіки |
| `vi.mock("./price")` у `price.test.ts` | замоковано сам об'єкт тестування |

Мокають залежності, а не те, що тестують. Новий тест на граничний випадок чи рефакторинг на зелених тестах — нормальні зміни.

Після реалізації попросіть **окремий subagent** перевірити, чи не підігнано код під тести: свіжий контекст без упереджень автора.

## Перевіряйте, а не вірте

«Баг виправлено» — твердження, не доказ. Вимагайте вивід тесту, що тепер проходить, або запустіть перевірку самі.

## Швидкий цикл

```markdown
## Тести
- Один файл: `npx vitest run path/to/file.test.ts`
- Увесь набір (перед комітом): `npm test`
```

Такий блок у CLAUDE.md дає Claude швидку цільову перевірку під час ітерацій, а повний набір — перед комітом чи в CI. Автоматичний запуск на подію — це вже hook ([[dev-cc-automation]]).

## Складні випадки

- **Flaky-тест**: не `retry(3)` і не `skip`, а пошук причини — гонки, залежність від порядку чи часу, спільний стан — і детерміноване відтворення.
- **Легасі без тестів**: спершу характеризаційні тести, що фіксують поточну поведінку, потім рефакторинг із зеленими тестами. Див. [[dev-cc-boss]].
