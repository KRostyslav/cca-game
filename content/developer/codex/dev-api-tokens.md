## Поле `usage`

Фактичний облік конкретного запиту, за яким виставляють рахунок:

```json
"usage": {
  "input_tokens": 120,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 18000,
  "output_tokens": 410
}
```

- Повний вхід = `input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens`. `input_tokens` — лише некешована частина.
- Thinking входить в `output_tokens`, навіть якщо текст міркувань приховано.
- Вихідні токени помітно дорожчі за вхідні.
- `cache_read_input_tokens: 0` на повторюваних запитах означає, що префікс змінюється (наприклад, час у `system`) — див. [[dev-caching-cost]].

Облік: логувати `usage` і `model` з кожної відповіді, множити кожне поле на ставку цієї моделі, агрегувати за фічами чи клієнтами. Довжина рядка — не токени.

## Підрахунок до запиту

`client.messages.count_tokens(...)` (`POST /v1/messages/count_tokens`) приймає ті самі `model`, `system`, `tools`, `messages` і повертає `input_tokens`. Він безкоштовний, має власні rate limits і дає **оцінку**, яка може трохи відрізнятись від `usage`, — пороги ставлять із запасом.

Не підходять: `tiktoken` (чужий токенізатор) і «символи / 4». Різні моделі можуть токенізувати той самий текст по-різному, тож при міграції бюджет перераховують.

## Що займає контекст

Визначення `tools`, `system`, уся історія `messages` (разом з `tool_result`) і сам вихід. Заголовки — ні. 30 інструментів додають тисячі вхідних токенів до кожного запиту. Зображення рахуються як вхідні токени пропорційно площі — зменшуйте їх до потрібної роздільності.

Без кешування й стискання N-й запит розмови містить усі попередні ходи: сума росте приблизно квадратично.

Захист від переповнення:
1. `count_tokens` для запиту.
2. Порівняти з `max_input_tokens` моделі мінус запас під `max_tokens`.
3. Якщо не влазить — стиснути старі ходи, зберігши ключові факти.
4. Надіслати й звірити `usage`.

Вхід реально здешевлюють кешування стабільного префікса, прибирання зайвих інструментів і ходів, менші зображення. `max_tokens` і streaming на вхід не впливають.

## `stop_reason`

| Значення | Що робити |
|---|---|
| `end_turn` | Природне завершення |
| `max_tokens` | Відповідь обрізана: не парсити, збільшити ліміт або зменшити задачу |
| `stop_sequence` | Спрацювала стоп-послідовність |
| `tool_use` | Виконати інструмент ([[dev-tool-loop]]) |
| `pause_turn` | Продовжити хід (server tools) |
| `refusal` | HTTP 200, але відмова: показати окреме повідомлення, деталі в `stop_details` |

`max_tokens` — запобіжник, про який модель не знає: низьке значення не робить відповідь стислою, а обриває її. Перевіряйте `stop_reason` **до** читання `content`.
