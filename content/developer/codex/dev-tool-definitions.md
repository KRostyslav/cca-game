## Анатомія визначення

```json
{
  "name": "search_orders",
  "description": "Шукає замовлення клієнта за ID. Викликай, коли користувач питає про статус замовлень. Повертає до 20 записів; для пошуку клієнта за email використовуй find_customer_by_email.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_id": { "type": "string", "description": "ID клієнта, напр. cus_123" },
      "status": { "type": "string", "enum": ["open", "shipped", "cancelled"] }
    },
    "required": ["customer_id"]
  }
}
```

| Поле | Роль |
|---|---|
| `name` | Ідентифікатор для диспетчеризації, `^[a-zA-Z0-9_-]{1,64}$` — без пробілів, крапок і кирилиці |
| `description` | Промпт вибору: що робить, **коли** викликати (і коли ні), що повертає, обмеження, межа з сусідніми інструментами |
| `input_schema` | JSON Schema аргументів; модель поверне їх у `tool_use.input` |
| `strict` | `true` — гарантія, що `input` точно відповідає схемі |

## Схема — теж промпт

- `enum` для скінченних множин значень;
- `description` кожної властивості з форматом і прикладом («ISO 8601, YYYY-MM-DD»);
- `required` — лише справді обов'язкові поля.

API **не** підставляє `default` — відсутнє поле обробляє ваш код. `$schema` не потрібен.

## strict tool use

`strict: true` — поле **самого інструмента**, поруч із `name`, а не в `tool_choice`. Схема має бути закритою: `additionalProperties: false` і `required`. Без `strict` модель зазвичай дотримується схеми, але не гарантовано: валідуйте `input` у коді, як будь-який неперевірений ввід, і на помилку повертайте `tool_result` з `is_error: true`.

## Tool Runner будує схему сам

```python
@beta_tool
def get_weather(city: str, unit: str = "celsius") -> str:
    """Повертає поточну погоду в місті."""
```

Типи беруться з анотацій, опис — з docstring, `required` — параметри **без** значення за замовчуванням (тут лише `city`).

## Anthropic-defined інструменти

Bash, text editor, memory оголошують через `type` без схеми: `{"type": "bash_20250124", "name": "bash"}`. Власний інструмент з `name: "bash"` і своєю схемою — це вже інший, користувацький інструмент. Виконує їх однаково ваш код (див. [[dev-server-tools]]).

## Вартість і кеш

Визначення входять у вхідні токени **кожного** запиту. Порядок рендерингу — `tools` → `system` → `messages`, тому:

- сортуйте інструменти детерміновано;
- не вставляйте час чи інші змінні дані в описи;
- інакше `cache_read_input_tokens` лишатиметься нулем.

Коли інструментів десятки, позначайте рідковживані `defer_loading: true` і додайте tool search tool — модель підвантажить потрібні визначення сама. Далі: [[dev-tool-loop]].
