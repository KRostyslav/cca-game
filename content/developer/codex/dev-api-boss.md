## Принципи

Продакшн-клієнт має бути **передбачуваним**, **спостережуваним** і **чесним щодо збоїв**. Власні обгортки над `fetch` з ручним SSE-парсером і розбором текстів помилок — джерело багів: беріть офіційний SDK і пишіть логіку поверх нього.

## Чекліст

| Область | Що зробити |
|---|---|
| Модель | Фіксований ідентифікатор, явний `effort` замість дефолтів |
| Ключ | Лише на бекенді, у сховищі секретів; ключ із фронтенд-бандла — відкликати |
| Доставка | Streaming для чату й довгих виходів ([[dev-api-streaming]]) |
| Завершення | Обробка кожного `stop_reason` плюс запасна гілка |
| Помилки | Повтори лише тимчасових, деградація після вичерпання ([[dev-api-errors]]) |
| Облік | `request-id`, `model`, `usage` з усіма кешованими полями, `stop_reason` |
| Контекст | Вимірювання, стискання зі збереженням фактів, кешування префікса |

## Обробник завершення

```python
match msg.stop_reason:
    case "end_turn" | "stop_sequence": deliver(msg)
    case "max_tokens": mark_truncated(msg)
    case "refusal": show_refusal(msg.stop_details)
    case _: log_unknown(msg)
```

`max_tokens` і `refusal` — успішні відповіді 200 без винятку, тому без перевірки користувач побачить обривок або порожнечу. У потоці `stop_reason` приходить у `message_delta`.

## Скелет обробки повідомлення

1. Додати повідомлення в історію, оцінити розмір `count_tokens`.
2. За потреби стиснути старі ходи.
3. `messages.stream(...)`, пересилати `text_delta`.
4. На `message_delta` зафіксувати `stop_reason` і `usage`.
5. Зберегти фінальний `content` в історію, записати лог з `request-id`.

Історія для API й лог для людей — різні речі: в API повертають `content` без змін (особливо `thinking` і `tool_use`), компактне представлення будують окремо.

## Типові пастки

- **Облік без кешу.** Сума лише `input_tokens` + `output_tokens` занижує витрати після ввімкнення кешування: запис у кеш дорожчий за звичайний вхід, читання — дешевше.
- **Штурм лімітів.** 200 паралельних запитів → хвиля 429. Для офлайн-обсягів — Message Batches ([[dev-batch-latency]]), інакше паралельність за `anthropic-ratelimit-*`.
- **Дубль побічних ефектів.** Повтор ходу агента списав гроші двічі — ідемпотентність у самому інструменті.
- **Обрив потоку.** `overloaded_error` посеред відповіді: показати, що відповідь перервана, не зберігати обривок, повторити з backoff.
- **Міграція моделі.** Прибрати `temperature`/`top_p`/`top_k`, замінити `budget_tokens` на adaptive thinking з `effort`, прогнати evals і перерахувати бюджет. Ендпоінт і формат `messages` не змінюються.
- **Latency.** Час до першого токена скорочують streaming і нижчий `effort` чи швидша модель, підтверджені eval-ом, а не мінімальний `max_tokens`.
- **Довгі розмови.** Більше вікно лише відсуває межу; потрібні стискання історії й кешування ([[dev-api-tokens]]).

Для розслідувань достатньо `request-id` разом з моделлю, `stop_reason` і `usage` ([[dev-observability]]).
